01 Context & Scope

Jira: NSP-19 — Super Admin can rename and merge departments/verticals at HO, with linked cases and letters arranged for access.

ℹ

Scope: HO departments and verticals only. RO/TE support deferred to a follow-up ticket.

Requirements

  • Rename — Change department/vertical name and short code at HO
  • Merge — Combine two HO departments/verticals into one, reassigning users
  • Access — Linked cases and letters remain accessible after the operation
  • Multi-session — Each step can be performed independently; user can pause and resume later
  • User-driven — Every action shows affected artifacts and lets the user trigger the action

02 Key Decisions

📄

Historical Data

Existing cases and letters keep the old department name. Only new items use the renamed department. Preserves audit trail.

👥

Group Handling

After moving members, old groups are kept empty (not deleted). ACLs on existing cases remain valid. Safe rollback option.

✅

User Control

Every step shows a grid of affected artifacts with action buttons. User decides when to execute each step. Multi-session capable.

🏠

Scope

HO departments/verticals first. RO/TE deferred to follow-up ticket.

04 Rename Workflow

Rename — End-to-end flow
sequenceDiagram
    actor Admin as Super Admin
    participant UI as Dept Admin Page
    participant API as Spring Boot API
    participant DCTM as Documentum

    Admin->>UI: Select department to rename
    UI->>API: GET /api/admin/departments/groups?prefix=ecm_ho_{old}
    API->>DCTM: DQL: SELECT group_name FROM dm_group WHERE group_name LIKE 'ecm_ho_{old}%'
    DCTM-->>API: List of groups
    API-->>UI: Display groups in grid

    Note over Admin,UI: Step 1: Review affected groups (pausable)

    Admin->>UI: Enter new name + short code
    UI->>API: GET /api/admin/departments/users?deptShortCode={old}
    API->>DCTM: DQL: SELECT ... FROM cms_user_profile WHERE department_short_code_multi
    DCTM-->>API: List of users
    API-->>UI: Display users in grid

    Note over Admin,UI: Step 2: Review affected users (pausable)

    Admin->>UI: Click "Create New Groups"
    loop For each old group
        UI->>API: POST /api/admin/departments/groups/create
        API->>DCTM: POST /groups (create ecm_ho_{new}*)
    end

    Note over Admin,UI: Step 3: Create new groups (pausable)

    Admin->>UI: Click "Move Members" per group row
    loop For each member in group
        UI->>API: POST /api/admin/departments/groups/{target}/members
        API->>DCTM: POST /groups/{target}/users
        UI->>API: DELETE /api/admin/departments/groups/{source}/members/{member}
        API->>DCTM: DELETE /groups/{source}/users/{member}
    end

    Note over Admin,UI: Step 4: Move members (per-group action buttons)

    Admin->>UI: Click "Update User Profiles"
    loop For each user
        UI->>API: PATCH /api/admin/departments/users/{objectId}
        API->>DCTM: POST /objects/{objectId} (X-Method-Override: PATCH)
    end

    Note over Admin,UI: Step 5: Update user profiles (pausable)

    Admin->>UI: Click "Rename Folder"
    UI->>API: PATCH /api/admin/departments/folder/{folderId}
    API->>DCTM: POST /objects/{folderId} (rename object_name)

    Note over Admin,UI: Step 6: Rename folder (final step)

05 Rename — Wizard Steps

⚠

Multi-session: Each step is independent. The user can complete Step 1 today, Step 2 tomorrow, etc. The UI tracks completion status via API queries (checking if new groups exist, if members are moved, etc.).

Select Department & Enter New Name

User selects the HO department to rename from a dropdown. Enters the new department name and new short code.

User Input

UI: Dropdown + text inputs. Validates short code uniqueness.

Review Affected Groups

System queries all groups matching ecm_ho_{oldShortCode}% and displays them in a data grid.

Grid columns: Group Name | Members Count | New Group Name (auto-generated) | Status

Pausable — Review only

API: GET /api/admin/departments/groups?prefix=ecm_ho_{old}

Create New Groups

For each old group, the system shows the proposed new group name. User clicks "Create All" or creates individually via row action buttons.

Grid columns: Old Group | New Group | Action [Create] | Status [Pending/Created/Failed]

User Action — per row or bulk

API: POST /api/admin/departments/groups/create body: {groupName}

Move Members (Group by Group)

For each group pair (old → new), display members in a grid. User clicks "Move All" per group or selects individual members.

Grid columns: Member Name | Type (User/Group) | Source Group | Target Group | Action [Move] | Status

Each row has a "Move" button. Bulk "Move All Members" button per group.

User Action — per member or per group

API: POST /api/admin/departments/members/move body: {sourceGroup, targetGroup, memberName, memberType}

Update User Profiles

Display all users whose department_short_code_multi contains the old code. Grid shows current vs new values.

Grid columns: User Name | Login | Current Dept | New Dept | Action [Update] | Status

User clicks "Update All" or updates individually.

User Action — per user or bulk

API: PATCH /api/admin/departments/users/{objectId} body: {department_name, department_short_code_multi}

Rename Department Folder

Rename the folder /ECM CONFIG/Office Type/HO/{oldName} to the new name.

Display: Current folder name → New folder name. Single action button.

Final Step

API: PATCH /api/admin/departments/folder/{folderId} body: {object_name: newName}

08 Merge — Wizard Steps

Select Source & Target Departments

User selects the department to merge FROM (source) and the department to merge INTO (target).

UI: Two dropdowns side-by-side. Validation: source ≠ target.

User Input

Review Group Mapping

System auto-maps source groups to target groups by suffix pattern. Displays mapping grid.

Grid columns: Source Group | Members | Target Group | Target Exists? | Action

Pausable — Review mapping

ℹ

Auto-mapping rule: ecm_ho_{sourceCode}_{suffix} maps to ecm_ho_{targetCode}_{suffix}. If target doesn't exist, flagged for creation in Step 4.

Review User Impact

Shows all users in source department with current and proposed values.

Grid columns: User Name | Login | Current Dept | New Dept | Groups Changing | Status

Pausable — Review only

Create Missing Target Groups

If any source groups don't have a matching target, create them. Grid shows which need creation.

Grid columns: Group to Create | Based on Source | Action [Create] | Status

User Action — per row or bulk

Move Members (Group by Group)

Same UX as Rename Step 4. For each source→target group pair, show members grid with individual and bulk move buttons.

Grid columns: Member | Type | Source | Target | Action [Move] | Status

User Action — per member or per group

Update User Profiles

Update department_name and department_short_code_multi for all source users.

Grid columns: User | Current Dept | New Dept | Action [Update] | Status

User Action — per user or bulk

Verify & Summary

System verifies: source groups empty, all users updated, target groups have correct members.

Display: Summary card with counts — groups processed, members moved, users updated, any failures.

11 Backend Service

DepartmentAdminService.java

New service providing granular operations (not bulk). Each API call is atomic — supports multi-session by design.

MethodDQL / REST Call
findGroupsByPrefix(prefix)DQL: SELECT group_name, description FROM dm_group WHERE group_name LIKE '{prefix}%' + count members per group
getGroupMembers(groupName)REST: GET /groups/{name} → extract users_names, groups_names
createGroup(groupName)REST: POST /repositories/{repo}/groups with {properties: {group_name}}
moveMember(source, target, member, type)REST: POST /groups/{target}/users then DELETE /groups/{source}/users/{member}
findUsersInDept(deptShortCode)DQL: SELECT ... FROM cms_user_profile WHERE ANY department_short_code_multi = '{code}'
updateUserDept(objectId, newDept, newCode)REST: POST /objects/{id} with X-Method-Override: PATCH
getDeptFolder(path)DQL: SELECT r_object_id, object_name FROM dm_folder WHERE ANY r_folder_path = '{path}'
renameFolder(folderId, newName)REST: POST /objects/{id} with X-Method-Override: PATCH, {object_name: newName}

12 Frontend Page

DepartmentAdminPage.jsx

Route: /dashboard/dept-admin — Two top-level tabs: Rename | Merge

Wizard Component Pattern

  • Step indicator at top (numbered circles with labels, current step highlighted)
  • Content area with data grid for current step
  • Action buttons per row (Move, Create, Update) + bulk action button
  • Status column per row: Pending Processing Done Failed
  • Navigation: Back | Next Step | Save Progress & Exit
  • "Save Progress & Exit" allows leaving mid-wizard. On return, system detects completed steps by querying current state (do new groups exist? are members moved?)

Multi-Session State Detection

StepHow to Detect Completion
Groups CreatedQuery GET /groups?prefix=ecm_ho_{newCode} — if groups exist, step done
Members MovedQuery old group members count — if 0, step done for that group
Users UpdatedQuery GET /users?deptShortCode={oldCode} — if 0 users, step done
Folder RenamedQuery folder by new path — if exists, step done

14 Safety & Rollback

🔒

Old Groups Preserved

Source groups are emptied but never deleted. ACLs on existing cases/letters referencing old groups remain valid. Rollback: move members back.

📄

Historical Data Untouched

Existing cms_case_folder and cms_digidak_folder objects are not modified. Only user profiles and groups are changed.

👁

User-Driven Execution

Every operation requires explicit user action. No automatic bulk operations without review. Each row visible before action.

📝

Audit Logging

Every group create, member move, and user update is logged via SLF4J with [DeptAdmin] prefix. Full traceability.

Rollback Procedure

  1. Move members from new groups back to old groups (same UI, reverse direction)
  2. Update user profiles back to old department name/code
  3. Rename folder back to old name
  4. Delete the new (now empty) groups if desired
