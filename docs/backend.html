Backend

Where the weight sits

DigidakService (1,729 lines), UserService (1,191) and RajbhashaService (1,064) account for roughly a third of all service code. RajbhashaService is disproportionate to its two endpoints because it builds Hindi-language reports with Apache POI — poi-ooxml 5.2.3 is a dependency purely for that.

The DQL layer

Every service builds DQL as a Java string and posts it to dctm-rest. The recurring shape:

String safe = username.replace("'", "''");
String dql  = "SELECT group_name FROM dm_group WHERE ANY users_names = '" + safe + "' ORDER BY group_name";
String url  = dctmConfig.getUrl() + "/repositories/" + dctmConfig.getRepository()
            + "?dql={dql}&items-per-page=200&page=1&inline=true";

Map<String, Object> response = restClient.get()
        .uri(url, dql)
        .header("Authorization", getAuthHeader())
        .header("Accept", "application/vnd.emc.documentum+json")
        .retrieve()
        .body(Map.class);

Then the envelope is unwrapped by hand:

entries[] → entry.get("content") → content.get("properties") → the values you wanted

Quote-doubling is the only injection defence. value.replace("'", "''") appears throughout. It is applied inconsistently — some paths interpolate values that were never escaped. Any new query should escape every interpolated value, and /api/query/execute deliberately accepts arbitrary DQL from the client, so that endpoint is a full repository console for anyone who can reach it.

cms_user_profile has no user_name attribute. It carries the display name in object_name and the login in user_login_name. Since group membership is keyed on dm_user.user_name, code that compares a profile against a group member list must use object_name. Getting this wrong fails silently — the comparison simply never matches. It has already caused a defect in EditUserProfileModal.

Group cleanup — the part that surprises people

Updating a user profile does more than write attributes. UserService.handleDepartmentChange runs on save and removes group memberships that no longer match the profile. It branches on office type:

// HO: drop every ecm_ho_* group whose leading segment is not a selected department
String deptCode = extractDeptCodeFromHOGroup(groupName);   // first segment after "ecm_ho_"
if (deptCode != null && !newDeptCodesLower.contains(deptCode)) {
    groupService.removeMember(groupName, dmUserName, "user");
}

// RO/TE: drop groups containing "_<newDept>_"

Known defect. extractDeptCodeFromHOGroup("ecm_ho_vertical_head_ddsi_<vertical>") returns "vertical", never "ddsi", because it takes the first segment after the prefix. "vertical" is never a selected department, so vertical-head groups are removed on any HO department change — including one where that vertical's own department is retained, silently orphaning the vertical. Tracked on NEO-239; the fix is to teach the method to recognise the vertical_head_ segment.

dm_superusers_dynamic and ecm_local_admin are excluded from cleanup, so they survive every profile change — including one that marks a user RETIRED.

Build

cd backend
mvn spring-boot:run      # dev server on 8080
mvn clean install        # build (produces neoadminBackend.war)
mvn test                 # runs nothing — no tests exist

Maven is used directly; there is no wrapper (mvnw is gitignored). Lombok supplies @RequiredArgsConstructor and @Slf4j and is configured as an annotation processor in both the compiler and Spring Boot plugins.
