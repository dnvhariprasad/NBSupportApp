Code patterns

The conventions that repeat across this codebase, and the traps that have already produced defects. Read this before changing anything.

Backend conventions

Constructor injection via Lombok

@Service
@Slf4j
@RequiredArgsConstructor
public class GroupService {
    private final RestClient restClient;
    private final DctmConfig dctmConfig;
}

No @Autowired anywhere. Logging is @Slf4j; there is no System.out.println.

Thin controller, fat service

@GetMapping("/{groupName}/members")
public Map<String, Object> getGroupMembers(@PathVariable String groupName) {
    return groupService.getGroupMembers(groupName);
}

Controllers unpack parameters and delegate. All logic, all DQL and all response shaping live in services.

Maps, not DTOs

Only AuthResponse and LoginRequest exist. Everything else returns Map<String, Object> or List<Map<String, String>>. When adding an endpoint, follow the surrounding style rather than introducing a DTO for one response — but be aware the compiler gives you no protection over key names.

Unwrapping the Documentum envelope

List<Map<String, Object>> entries = (List<Map<String, Object>>) response.get("entries");
for (Map<String, Object> entry : entries) {
    Map<String, Object> content = (Map<String, Object>) entry.get("content");
    if (content == null) continue;
    Map<String, Object> props = (Map<String, Object>) content.get("properties");
    ...
}

Repeated in nearly every service, with @SuppressWarnings("unchecked") on the method. Null-check content and properties: some rows legitimately lack them.

Escaping before interpolation

String safe = value.replace("'", "''");

The only defence against DQL injection. Apply it to every interpolated value, not just the obvious one.

Identifier semantics — the biggest trap

A user has three names, and they are not interchangeable.

FieldOnExampleUsed by
user_namedm_userSonny GeorgeGroup membership (dm_group.users_names)
user_login_namedm_user, cms_user_profilecto.ditLogin, OTDS
object_namecms_user_profileSonny GeorgeThe profile's display name — equals user_name

cms_user_profile has no user_name attribute at all. A DQL query selecting it fails with DM_QUERY_E_NOT_ATTRIBUTE.

The rule

  • Server-side: pass either form. GroupService.getGroupsByUser, addMember and removeMember all call resolveDmUserName first, so both work.
  • Client-side: when comparing a user against a group member list, use object_name (falling back to user_name, then user_login_name). Group member lists return user_name; the profile object carries object_name. Comparing on user_login_name fails silently.

This exact mistake shipped once: in the vertical-head prompt the outgoing head appeared in their own replacement dropdown, because the exclusion compared user_login_name ("cto.dit") against a member list containing user_name ("Sonny George").

Group naming

ShapeMeaning
ecm_ho_<dept>HO department group
ecm_ho_<dept>_<vertical>HO vertical — one level below the department
ecm_ho_vertical_head_<dept>_<vertical>HO vertical head
ecm_<ro>, ecm_<ro>_<dept>RO/TE office and department
ecm_<ro>_vertical_head_<dept>RO/TE vertical head — the department is the vertical here
ecm_digidak_ro_<code>_ddm, ecm_digidak_<office>_<dept>_cgmDigidak role groups
dm_superusers_dynamic, ecm_local_adminPreserved by group cleanup

HO and RO/TE nest differently. At HO a vertical sits below a department, so matching a department group against a vertical-head group requires a prefix comparison with an underscore boundary (head === derived || head.startsWith(derived + '_')). At RO/TE the department group is itself the vertical, so equality suffices. Code that only handles equality silently misses every HO case.

Non-ASCII group names

Group names can contain Devanagari, e.g. ecm_ho_vertical_head_ddsi_शिक्षण_प्रशिक्षण_और_कार्यशालाएँ. Always encodeURIComponent a group name before putting it in a URL.

api.get(`/groups/${encodeURIComponent(groupName)}/members`);

VerticalsPage.jsx still interpolates group names unencoded and is likely affected.

Dates

This portal reads xCP REST, which returns ISO-8601 UTC. DFC-backed screens elsewhere in the programme return a day-first string. Never format a Documentum date by hand — use utils/dateFormat.js:

import { formatDateTime } from '../utils/dateFormat.js';
formatDateTime(row.completion_date);   // → 16/01/2026 05:44:00 PM

On the Movement Register, r_creation_date, r_modify_date and completion_date are genuinely different moments, typically 20–40 seconds apart. They are distinct events, not one timestamp formatted inconsistently. NEO-247 resolved the reported "mismatch" by showing only Completion Date.

Frontend conventions

Local state, direct calls

const [rows, setRows] = useState([]);
const [loading, setLoading] = useState(false);
useEffect(() => { api.get('/…').then(r => setRows(r.data)).catch(() => {}); }, []);

No store, no query cache. Each page owns its own loading and error state.

Blocking guards before save

EditUserProfileModal uses a consistent shape for "this change is not allowed yet": a boolean show…Block plus a pending list, checked at the top of handleSubmit.

if (showPendingBlock) return;
if (showOfficeBlock)  return;
if (showDeptBlock)    return;
if (showLocationBlock) return;

Guards that must run before persistence belong ahead of the api.patch call, so that cancelling writes nothing. The vertical-head guard follows this rule deliberately.

Read-only controls

A disabled <select> with a single <option> and disabledSelectCls, wrapped in SelectWrapper. Used for HO location, auto-filled short codes, and the RETIRED/TRANSFERRED markers.

Do not define components inside components

VerticalsPage declares VerticalHeadModal inside the page body, so it is re-created on every render and its <select> remounts. AssignVerticalHeadModal was extracted to its own file specifically to avoid repeating that. Put new modals in components/.

The payload-builder trap

handleSubmit destructures department_short_code_multi out of the form and re-adds it only inside office-type branches:

const { department_short_code_multi, ...rest } = form;
const payload = {
  ...rest,
  ...(isHO    && { department_short_code_multi: … }),
  ...(isROTE  && !isDDMUser && { department_short_code_multi }),
  ...(isDDMUser && { department_short_code_multi: … }),
  ...(isExit  && { department_short_code_multi: [form.office_type] }),
};

Any new office type that matches none of these branches loses the field entirely — silently, with no error. The last branch exists because RETIRED and TRANSFERRED hit exactly that hole.

Where authority actually lives

Group cleanup on profile save is performed by the backend (UserService.handleDepartmentChange), not by the removal loop in EditUserProfileModal. Frontend logic that tries to predict what will be removed must model the backend rule. Mirroring the frontend loop produces a guard that stays silent exactly when it matters — that is how the first version of the NEO-239 guard missed every office-type change.

Metadata pattern

For new metadata types, follow the Case Type implementation (techdocs/case-type-metadata.md):

  1. Store entries as dm_folder objects under /ECM CONFIG/<Metadata Name>/.
  2. MetadataService: add list<Name>() (SELECT r_object_id, object_name FROM dm_folder WHERE FOLDER('/ECM CONFIG/<Name>')) and create<Name>(String objectName), resolving the parent via resolveFolderInfo() and inheriting its ACL.
  3. MetadataController: GET and POST /api/metadata/<name>s.
  4. MetadataPage.jsx: a <Name>Tab with a create form and list, wired into the right tab group.

UI conventions

  • Functional components, PascalCase filenames.
  • Tailwind for all styling; brand blue #0A66C2.
  • Framer Motion timings: 150 ms hover, 300 ms modal, 500 ms page.
  • Modals: max 70 vh, fixed header and footer, scrollable body with scrollbar-thin.
  • Skeletons for initial load, spinners for actions.
  • Toasts top-center/right — 3 s success, 5 s error.
  • Server-side pagination beyond 50 rows.
  • Destructive actions use inline two-step confirmation — never window.confirm().

Hard constraints

  • services/dctm-rest/ is read-only. Never modify it; use services/dctm-rest/docs/rest.yaml as API reference.
  • RestClientConfig trusts all TLS certificates. Required for the self-signed Documentum endpoint — do not copy that pattern into anything internet-facing.
  • /api/query/execute accepts arbitrary DQL. Useful for diagnosis, dangerous if exposed.
  • No tests exist. Verify by running the app and querying the repository.
